DATA CURATION PLAN
Curated Synthetic Healthcare Datasets
Version 1.0.0

1. About these files

This plan describes the curated healthcare datasets in this folder. The files
were created synthetically and contain fictional information.

2. What is included

The folder contains 25 plain-text documents. These documents are the complete
data-curation output for this branch.

| Dataset category                       | Count | Location                         |
|---------------------------------------|------:|----------------------------------|
| Synthetic clinical notes              |    15 | curated-dataset/ (`DOC-CLIN-*`) |
| Documentation guidance                |     5 | curated-dataset/ (`DOC-GUIDE-*`) |
| Fictional payer-policy excerpts       |     5 | curated-dataset/ (`DOC-POLICY-*`) |
| Source documents                      |    25 | curated-dataset/                |

3. Important notes

All records are fictional. They must not be used for patient care, medical
advice, coding, billing, legal interpretation, or payer decisions.

4. Curation principles

Synthetic data

- Every name, identifier, date, facility, organization, provider, and narrative
  is fictional.
- We will not copy, lightly edit, or de-identify real clinical notes.
- The dataset must not contain real patient data, PHI, PII, provider names, payer
  names, phone numbers, email addresses, account numbers, or addresses.
- Clinical records use patient IDs in the form `SYN-P###` and encounter IDs in
  the form `SYN-ENC-###`.

Clear evidence boundaries

- A confirmed diagnosis must be kept separate from a symptom, medication,
  laboratory result, family-history statement, negated finding, or suspected
  condition.
- The documents should make these differences clear so the system does not make
  claims that the evidence does not support.
- A source should not imply a cause-and-effect relationship unless it says so
  directly.
- One laboratory result alone must not be treated as a diagnosis.

Consistent patient histories

- Each synthetic patient has three documents in a sensible chronological order.
- Acute, chronic, historical, resolved, and ongoing conditions must be clearly
  identified.
- Later notes may add information only when the change makes clinical sense.
- Information must never be carried over from one patient to another.

Easy-to-read writing

- Clinical notes should use familiar headings and normal clinical language.
- Important qualifiers should appear close to the diagnosis or finding they
  describe.
- Notes should include enough context to feel realistic, but they must not be
  written as answer keys.
- Common synonyms and abbreviations may be used naturally. Repeating the same
  wording should be avoided when possible.
- Stable document IDs must be available for source and chunk citations.

5. Dataset structure

Patient charts

| Patient ID | Documents | Scenario | Evidence boundary |
|------------|----------:|----------|-------------------|
| SYN-P001 | 3 | Diabetes and hypertension with one reduced eGFR result | The lab result does not establish CKD; no diabetic complication is documented |
| SYN-P002 | 3 | Heart-failure hospitalization and stable COPD | Acute and chronic conditions are separated; there is no COPD exacerbation |
| SYN-P003 | 3 | Hypertension and osteoarthritis | Diabetes appears only as family history; COPD is denied |
| SYN-P004 | 3 | Confirmed stage 3b CKD and hypertension | CKD is explicit; anemia is still being evaluated |
| SYN-P005 | 3 | Previous ischemic stroke with ongoing hemiparesis | The old stroke is separated from its lasting effects |

Guidance and policy documents

| Category | IDs | Coverage |
|----------|-----|----------|
| Documentation guidance | DOC-GUIDE-001 to DOC-GUIDE-005 | Evidence, condition status, specificity, attribution, and human review |
| Fictional payer policies | DOC-POLICY-001 to DOC-POLICY-005 | Evidence acceptance, completeness, review, escalation, and auditability |

6. Required metadata

Every source document starts with stable metadata. Clinical documents include:

| Field | Requirement |
|-------|-------------|
| DOCUMENT_ID | Unique and permanent, such as DOC-CLIN-P001-001 |
| DOCUMENT_TITLE | Readable title |
| DOCUMENT_TYPE | Specific type, such as `primary_care_progress_note` |
| DATA_CLASSIFICATION | Always `SYNTHETIC` |
| DOCUMENT_VERSION | `1.0.0` for the initial release |
| PATIENT_ID | Required for clinical documents; uses `SYN-P###` |
| ENCOUNTER_ID | Required for clinical documents; uses `SYN-ENC-###` |
| ENCOUNTER_DATE | Fictional ISO-8601 date |
| AUTHOR_ROLE | Fictional role, not a real clinician's identity |
| ORGANIZATION | Fictional organization only |

Guides and policies use DOCUMENT_OWNER and EFFECTIVE_DATE instead of patient
and encounter fields. Every file must also contain the synthetic-data notice
below.

SYNTHETIC MOCK DOCUMENT
This document contains fictional, synthetically created data. It is
not intended for clinical care, coding, billing, legal interpretation, or payer
submission.

7. Writing the documents

Clinical notes should use the sections that fit the scenario, such as:

- Reason for visit or interval history
- Relevant history and current medications
- Symptoms, examination, and selected laboratory observations
- Assessment and plan
- Follow-up instructions or care coordination

Guidance and policy documents should use short numbered sections, examples, and
clear limits. They must not copy official coding manuals, CMS guidance, or real
payer rules. The fictional organization is called SYNTHETIC PAYER ALPHA.

8. Curation workflow

1. Confirm the 25-document inventory and freeze the document IDs.
2. Define each patient's timeline, confirmed conditions, and evidence limits.
3. Write the clinical notes from the approved synthetic scenarios.
4. Check timelines, medication continuity, and patient separation.
5. Write the five documentation guides.
6. Write the five fictional payer-policy excerpts.
7. Check for placeholders, real-world identifiers, duplicate IDs, and missing
   disclaimers.
8. Mark the finished dataset as version 1.0.0.

9. Quality checks

The dataset is ready for ingestion when all of these checks pass:

- There are exactly 25 `.txt` files: 15 clinical notes, 5 guides,
  and 5 policies.
- Every document ID is unique.
- Every clinical document has valid patient, encounter, author-role, and date
  metadata.
- Every source contains the required synthetic-data notice.
- Dates move forward logically within each patient's chart.
- The charts clearly distinguish confirmed, historical, denied, family-history,
  laboratory-only, and uncertain information.
- All people, organizations, contact details, and identifiers are fictional.
- The dataset contains no test questions, expected answers, labels, scores, or
  benchmark splits.
